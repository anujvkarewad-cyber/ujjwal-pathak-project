## 2. Non-negotiables (hard constraints baked into the design)

1. **Daily MCQ Challenge is frozen.** 10 questions (7 normal + 3 case-study), date-seeded, student-ID-seeded, group-seeded, Group I/II mixes, both streak tracks, 10-minute timer, auto-submit — no code path in this project writes to, reads from, or alters `dailyMcqBank.ts`, `mcqMetadata.ts`, `learning-data.js`, or the Daily MCQ logic. A CI guard verifies their hashes stay unchanged after every release build.
2. **Personalization only in the new "AI Adaptive Practice" mode** — separate entry point, separate data namespace, separate mastery store keyed by chapterId. Daily stays fair and fixed.
3. **Existing student features untouched** — login, dashboard, focus room, study timer/tracker, study receipt, reports, notes, leaderboard, notifications, existing mentor backend integration, unlimited MCQ practice.
4. **Existing mentor features untouched** — all current Apps Script actions, sheet tabs, pages, and API contracts stay byte-for-byte compatible.
5. **Official ICAI catalog (94 chapters, May 2026 modules) is the only chapter authority.** The pipeline re-reads `icaiChapterCatalog.ts` at run time; any chapter not in it fails closed.
6. **No secrets in Git** — API keys, Drive credentials, and downloaded private source files are never committed. Only `.env.example` files are added.
7. **No student PII ever reaches the AI provider.** Generation requests contain only ICAI/RTP/MTP/PYQ source excerpts + catalog context.
8. **Student MCQ answers, mastery history, and adaptive history stay device-local by default.** Mentor analytics gets MCQ signal only through the explicit consent-based summary sync.

Principles:

- **AI generation and student analytics are separate systems.** Generation moves: Drive + ICAI + RTP/MTP/PYQ → drafts. Analytics moves: local mastery → consented summary. The only bridge is that published content is what students practice on, and chapterIds are what summaries are keyed by.
- **One published artifact tree serves web and mobile.** Both consume the same `published-manifest.json` + immutable chunk files, so "same approved content" is structural, not a convention.
- **Fail closed everywhere.** Every pipeline stage and every publish path asserts its invariants before writing output.

## 4. Content data model (canonical schemas)

Single source of truth stored in MongoDB, exported to JSON for students. All IDs are assigned by the pipeline (deterministic, e.g. ULID/nanoid with `adp-` prefix), never by the model.

### 4.1 Catalog (authority: `mobile/src/data/icaiChapterCatalog.ts`)

```jsonc
{
  "catalogRevision": "may-2026",        // synced from the official catalog file
  "chapterCount": 94,
  "chapters": [{
    "chapterId": "ch-law-03",           // official ID as in icaiChapterCatalog.ts

    "paper": "Paper 2",
```

### 4.3 Case scenario — one passage, four linked MCQs

```jsonc
{
  "scenarioId": "adp_s_ch-law-03_0002",
  "revision": 1,
  "chapterId": "ch-law-03",
  "passage": "…shared passage…",
  "icaiSourceRefs": [ … ],              // scenario-level refs (required)
  "calibrationRefs": [ … ],
  "questionIds": [                      // ordered sequence 1–4
    "adp_q_ch-law-03_0021",             // each has scenario: { scenarioId, seq: 1, blockTotal: 4 }
    "adp_q_ch-law-03_0022",
    "adp_q_ch-law-03_0023",
    "adp_q_ch-law-03_0024"
  ],
  "status": "auto_validated",
  "statusHistory": [ … ]
}
```

A scenario MCQ's own `scenario` block (`scenarioId`, `seq`, `blockTotal`) is the linkage the validators enforce. The **Daily MCQ Challenge is unaffected**: it continues to render individual case MCQs from its existing data files, never linked blocks. The new scenario blocks are consumed only by AI Adaptive Practice (and optionally Unlimited Practice, Phase 5 choice).

### 4.4 Chapter record (coverage + gate state)

```jsonc
{
  "chapterId": "ch-law-03",
  "catalogMatch": { "valid": true, "catalogRevision": "may-2026" },
  "coverage": { "plainApproved": 0, "plainTarget": 30,
                "scenariosApproved": 0, "scenariosTarget": 5,
                "scenarioMcqsApproved": 0, "scenarioMcqsTarget": 20 },
  "blockingErrors": [],
  "status": "needs_review",             // chapter-level aggregation
  "releaseCandidate": null              // { revision, at, by } when publishable
}
```

Per chapter: **30 plain + 5×4 scenario = 50 questions**; 94 chapters ≈ **4,700 questions**.

### 4.5 Published manifest + content addressing

```jsonc
// published-manifest.json (the single file both clients fetch first)
{
  "schemaVersion": 1,
  "revision": 7,                        // monotonic, incremented per publish
  "publishedAt": "…", "publishedBy": "mentor@…",
  "catalogRevision": "may-2026",
  "chapters": [
    {
      "chapterId": "ch-law-03",
      "counts": { "plain": 30, "scenarios": 5, "scenarioMcqs": 20, "total": 50 },
      "questionIds": ["adp_q_…", "…"],  // full ID list for diffing
      "chunkWeb": "chunks/ch-law-03.r7.3f8a1c.json",
      "chunkMobile": "chunks/m/ch-law-03.r7.3f8a1c.json",
      "contentHash": "sha256:3f8a1c…"  // hash of canonical (normalized) chapter JSON
    }
  ],
  "dailyMcqFrozen": { "learningDataHash": "sha256:…" }  // guard proving Daily data untouched
}
```

Chunk file names embed `revision + short hash` → **immutable, cacheable forever**; the manifest carries the pointer + full sha256 so clients can verify integrity and detect stale caches. Manifest itself gets an ETag; clients re-fetch only on revision change.

### 4.6 Supersession & revisioning

- Editing an **approved** question creates `revision N+1` (new `id` stays same, `revision` increments, old version → `superseded`). Editing a **draft** mutates in place with an audit row.
- Publish = atomic promotion of all approved `release_candidate` chapters into a new manifest revision. Old manifests stay downloadable (rollback + audit).
- Local mastery on devices is keyed by `chapterId` (+ questionId for per-question spaced repetition). Content revision migration = additive reconciliation against the manifest (new questionIds appear; removed/superseded questionIds drop out of rotation without breaking stored mastery).

## 5. AI generation pipeline (Node.js, new `content-pipeline/`)

### 5.1 Layout & tech

```
content-pipeline/
├── package.json                 # Node 20+, ESM
├── .env.example                 # ALL secret docs (see §5.4)
├── config/chapters.json         # synced snapshot of the 94-chapter catalog (derived from icaiChapterCatalog.ts)
├── src/
│   ├── stage-1-drive.mjs        # Google Drive sync + cache
│   ├── stage-2-extract.mjs      # PDF/DOCX/text extraction
│   ├── stage-3-normalize.mjs    # source normalization + chapter segmentation
│   ├── stage-4-map.mjs          # map fragments → official 94-chapter catalog (fail closed)
│   ├── stage-5-generate.mjs     # chapter-wise AI generation (batch, resumable)
│   ├── stage-6-validate-schema.mjs   # JSON Schema (ajv) vs §4 schemas
│   ├── stage-7-validate-content.mjs  # content invariants (§5.3)
│   ├── stage-8-duplicates.mjs   # exact-match + MinHash/shingle + embedding similarity
│   ├── stage-9-coverage.mjs     # concept coverage per chapter
│   ├── stage-10-stage.mjs       # write drafts to MongoDB, queue for mentor
│   ├── stage-11-publish.mjs     # gated: build web + mobile bundles + manifest
│   ├── stage-12-verify.mjs      # cross-build validation (web vs mobile vs DB)
│   ├── lib/{drive.mjs, extract.mjs, llm.mjs, db.mjs, hashing.mjs, similarity.mjs, audit.mjs}
│   └── ai/adapters/{openai.mjs, anthropic.mjs, gemini.mjs}   # provider pluggable
└── state/                       # gitignored: job checkpoints, resumes, cost logs
```

Each stage is an idempotent CLI step (`node src/stage-N-*.mjs --chapter ch-law-03`) writing to `state/` + Mongo. A chapter-level job can resume from any stage. Stuck/partial chapters never enter the review queue.

### 5.2 Stage behavior

| # | Stage | What it does | Fail-closed behavior |
|---|---|---|---|
| 1 | Drive sync | Service-account Drive API; downloads configured folders (Modules, RTP, MTP, PYQ) to `.cache/drive/` with sha256 + mtime; skips unchanged files | Download/checksum failure → chapter's source set incomplete → stage 4 blocks it |
| 2 | Extract | `pdf-parse`/`mammoth`/plain-text extraction; preserves page + section markers; emits per-file text with provenance | Extraction error → file flagged `EXTRACT_FAILED`, excluded from generation |
| 3 | Normalize | Strip headers/footers/watermarks; unify whitespace; split into labeled fragments by chapter anchors (title + number) | Fragment without a chapter anchor stays `UNMAPPED` and is never fed to the model |
| 4 | Map | Assigns every fragment to exactly one of the 94 chapters using the official catalog + RTP/MTP attempt metadata | **Any chapter that ends up with no mapped module fragment is BLOCKED — no generation.** Unmapped fragments are reported to the mentor, never silently dropped |
| 5 | Generate | Per chapter: 30 plain + 5 scenario blocks (4 linked MCQs each), in deterministic order; provider adapter; prompts include catalog context + module excerpts (concepts/rules/provisions/definitions/terminology) + RTP/MTP/PYQ excerpts **for style/difficulty/calibration only**; response parsed to §4 JSON | Any non-conforming response → retry (bounded); after retries, question marked `generation_failed`, chapter stays incomplete |
| 6 | Validate schema | ajv against full question/scenario schema (incl. enum values, required refs) | Schema failure → item blocked from review |
| 7 | Validate content | See §5.3 invariant list | Any **error** → blocked from review; **warnings** visible to mentor and must be resolved before chapter publish |
| 8 | Duplicates | Exact normalized hash; MinHash+shingle Jaccard vs source corpus (anti-copy) and vs entire existing question bank (anti-dup); optional embedding cosine as second pass | Similarity ≥ threshold → **BLOCKED** (auto-rejected, reported) |
| 9 | Coverage | Ensures every `learningPoint` of the chapter is covered by ≥1 question; flags over/under-represented concept tags | Uncovered learning point → chapter warning; mentor must ack before publish |
| 10 | Stage | Upserts drafts (`status: auto_validated`), builds Review Queue aggregates, writes audit rows | Any staged item missing validation record → not staged |
| 11 | Publish | Gated (§7.3); builds web + mobile chunk trees + `published-manifest.json`; atomic swap; audit | Gate fails → publish aborts, previous revision stays live |
| 12 | Verify | Re-reads published tree: web vs mobile diff (IDs, hashes, counts, scenario structure), zero non-published items, manifest↔chunk hash match, Daily-data hash unchanged | Any mismatch → release marked `VERIFY_FAILED`, never exposed to students |

### 5.3 Content validation invariants (stage 7) — mapped to your fail-closed list

| Invariant | Rule | Severity |
|---|---|---|
| Chapter mappable | chapterId must exist in official catalog and have mapped module source | ERROR |
| Question counts | per chapter exactly 30 plain, 5 scenarios, 20 scenario MCQs (50 total) | ERROR |
| Options | exactly 4 non-empty, pairwise-distinct, no option matching prompt verbatim, exactly 1 `correctOptionId` | ERROR |
| Single correct answer | distractor plausibility check (each distractor must be a defensible wrong answer — LLM self-check + heuristic scoring); `correctOptionId` must reference an existing option | ERROR |
| Source references | ≥1 `icaiSourceRefs` (module) + ≥1 `calibrationRefs` (RTP/MTP/PYQ) on every question/scenario | ERROR |
| Duplicates | similarity thresholds from stage 8 | ERROR |
| Scenario linkage | every scenario has exactly 4 questionIds; each of those has `scenarioId` matching + `seq` 1–4 + `blockTotal` 4; no question in two scenarios | ERROR |
| Attempt-specific legal/tax | model must tag `attemptSpecificRisk` where law/rates are attempt-sensitive; validator elevates to WARNING requiring explicit mentor confirmation; **no confirmation → chapter cannot publish** | WARNING→BLOCK |
| Draft leakage | stage 11 asserts every item in a bundle has `status ∈ {approved, release_candidate}` and hash equals the approved content hash | ERROR |
| Terminology | prompt/options/explanation checked against module glossary for official terminology deviations | WARNING |

### 5.5 Generation discipline

- **Calibration, not copying.** RTP/MTP/PYQ excerpts are sent to the model only as difficulty/style benchmarks with explicit "do not reproduce verbatim" instructions; the stage-8 similarity gate vs source corpus is the enforcement.
- **Deterministic output shape.** Pipeline assigns IDs/sequences; the model only fills content fields. Batch per chapter ≈ 35–40 calls (30 plain + 5 scenario blocks + validation passes), resumable, with a `--dry-run` cost estimate before any live run.
- **No student data in prompts.** Stage 5 assembles prompts solely from catalog + cached ICAI sources; there is no code path that can include student records.

### 6.2 Auth & roles

- The student-facing sync endpoint uses a **separate** lightweight credential (see §9.4) so student backend auth behavior is untouched.

### 6.3 Content APIs (`/api/content/*`, mentor-only)

```

                                       #   questionType, difficulty, status, hasWarnings)
GET  /api/content/questions?chapterId=&status=&filters…   # paginated
GET  /api/content/questions/{id}       # full detail incl. refs, similarity, history

                                       #   difficulty/conceptTags (audited; revision bump if approved)

GET  /api/content/scenarios/{id}       # passage + 4 linked questions as one block
```

### 7.3 Chapter publish gate (backend-enforced, mirror of the UI)

A chapter is publishable **only when** ALL hold:

1. 30 plain MCQs `approved`
2. 5 scenarios `approved`
3. All 20 scenario MCQs `approved`
4. Zero blocking validation errors; warnings all mentor-acknowledged
5. `icaiSourceRefs` + `calibrationRefs` present on every item
6. Catalog mapping valid (`catalogMatch.valid` + mapped module source)

Publish is transactional: build bundles → hash → write manifest revision N+1 → verify (stage 12) → expose. On any failure the previous revision stays live.

### 8.3 Rules for mentor signals (all computed from existing data + consented summaries; no raw answers needed)

- **Weak in a subject / chapter:** latest band ≤ Weak for that subject/chapter.
- **Repeated incorrect concepts:** same weak concept tags across ≥3 summary snapshots.
- **Improving:** band strictly increased over last ≥2 snapshots; **declining:** strictly decreased.
- **No recent activity:** last activity date > threshold (default 14 days; configurable) across tracker + summaries.
- **Not yet assessed:** 0 attempts on all chapters (from summaries) or no tracker rows.
- **Ready for advanced:** ≥X chapters (default 60%) at Strong+ → suggest hard-difficulty adaptive sessions.
- **Intervention required:** declining trend AND (attendance drop OR tracker misses) → follow-up action drafted.

### 8.4 Student-level analysis view

Profile · Group · Attempt · Study activity (hours/attendance/tracker streak) · Subject performance · Chapter mastery (band per chapter) · Weak concepts (tags) · Recent improvement (band trend sparkline) · Recommended next action (rule-generated) · Last activity · Mentor notes + follow-up status (existing MentorNotes flow preserved).

### 8.5 Mastery bands (device-authoritative, sent as summary)

| Band | Rule (computed on device, from local mastery) |
|---|---|
| Not assessed | attemptCount = 0 |
| Weak | attempts ≥ 1, accuracy < 50% |
| Medium | 50–69% |
| Strong | 70–84% |
| Mastered | ≥ 85% and attempts ≥ minimum (default 5) |
| No recent activity | overlay: lastActivityDate older than threshold; colors the cell distinctly on top of its band |

Heatmap cells use these six visual states. Bands are always computed on the student device from local data; the mentor backend stores and displays, never recomputes from raw answers (it has none).

## 9. Student MCQ privacy & consent design

### 9.1 Default posture

- Student MCQ **answers, mastery history, adaptive history: device-local, not sent** by default.
- No raw answers flow to the production mentorship backend through any new path.
- The AI provider never receives any student data (generation is source-material-only, §5.5).

### 9.2 Consent-based summary sync (only thing that may leave the device)

Payload (matches your allowlist exactly, plus a time-series of the same fields for trend detection):

```jsonc
{
  "studentId": "…", "consentVersion": 1, "syncedAt": "…",
  "summaries": [{
    "chapterId": "ch-law-03",
    "masteryBand": "Strong",            // enum from §8.5
    "attemptCount": 42,
    "accuracyRange": "70-84",           // bucketed, never exact
    "lastActivityDate": "2026-08-15",
    "weakConceptTags": ["…", "…"]       // max 8 tags
  }],
  "trend": [{                            // ≤12 weekly snapshots of the SAME fields
    "weekStart": "2026-07-20", "chapterId": "ch-law-03",
    "masteryBand": "Medium", "attemptCount": 30, "accuracyRange": "60-69"
  }]
}
```

Constraints enforced server-side: ≤94 chapter summaries per student, bucketed ranges only, size caps, rate limit, schema validation. Everything else is rejected.

### 9.3 Student setting

**"Share learning progress with mentor: On/Off"** — visible in the student app settings (web + mobile). Behavior:

- **On →** device periodically (and on demand) pushes summaries via `/api/progress-sync`.
- **Off (default) →** device sends nothing; a consent-off record is written once (via `/api/consent`) so the mentor side knows sharing is disabled rather than stale.
- **Revoke →** mentor analytics stops including that student's MCQ summaries at query time; stored rows are retained but excluded and marked with the revocation timestamp. (Retention vs purge = Open Decision OD-5.)
- Toggle state is audited on both sides.

### 9.4 Access control & audit

- Mentor access to analytics APIs: JWT role `mentor` only; every analytics read writes a row to `content_audit` (actor, studentId, endpoint, time) → audit history visible in the dashboard.
- The sync credential: a per-student sync token minted by the mentor backend and distributed through the existing student↔mentor channel, validated against the existing Students registry (Apps Script `students.list`), so no change to the existing student backend or login is needed. (Final auth shape to be confirmed once the student repo is visible — OD-6.)
- Separate tables/namespace: `analytics_*` collections are physically separate from content and from anything the student backend uses.

```

        ▼
   Student web (vanilla JS)              Student APK (Expo/RN)
```

- **Web:** keeps its immediate catalog/manifest + existing Daily MCQ data untouched. New `adaptive-practice.js` lazy-loads only the chapters the student needs, verifies sha256 against the manifest, caches in IndexedDB/localStorage, and serves the new AI Adaptive Practice mode.

Compares web vs mobile vs DB:

- Same `revision` + `catalogRevision` · same chapterIds · same questionIds (set equality) · same content hashes · correct question counts (30/5/20 per chapter) · correct scenario structure (5 blocks × 4 linked) · **zero non-published items** (draft leakage check) · Daily-data hash unchanged (`dailyMcqFrozen` guard).
